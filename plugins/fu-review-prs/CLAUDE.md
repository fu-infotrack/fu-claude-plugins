## Design

- **PR-review orchestrator** (`fu-review-prs`): all irreversible/external steps (lock, state, GitHub post) are deterministic bash in the orchestrator; the per-PR review runs in a sub-agent whose context never returns. State (`last-reviewed-<pr>`: commit + tree SHA) is namespaced per repo and lives in `~/.claude/pr-review/`, outside the wiped plugin cache. The dedicated review clone is force-reset to a pristine `origin/main` at tick start **and** after each PR via `pr_review_reset_tree` (`fetch` → `checkout -f main` → `reset --hard origin/main` → `clean -fd` → prune all non-`main` local branches). Cross-Bash-call locks use a background `flock` holder process (a normal fd-flock would release when the bash call returns). The pre-flight→post handoff is **disk-based, not context-carried**, so a mid-tick context compaction loses nothing: pre-flight persists `pending-<pr>` (commit+tree) and the sub-agent writes `findings-<pr>.json`; `pr_review_finish <pr>` takes only the PR and recovers commit/tree/findings from disk. **The orchestrator's context sees tokens only** (v0.4.0), because a `/loop` session accumulates every tick's context. `log()` writes to the file and never to stderr, which the Bash tool would capture. Pre-flight prints `PROCEED` followed by the complete Task prompt (`dispatch_prompt`), so the model never assembles it. The sub-agent's whole reply is `DONE`, which the command says to ignore. `test/preflight.test.sh` pins exactly this stdout/stderr shape. **Pre-flight owns the review scope** (v0.5.0). `write_review_scope` picks the mode from the **tree** SHA, the same key the state uses: no state or an unchanged tree (a re-request) → FULL; a changed tree → DELTA over the PR's files (`pulls/files --paginate`) ∩ the files in `compare/<last>...<head>`. It writes `scope-<pr>.txt` (a `REPO`/`HEAD`/`MODE`/`DELTA_BASE` header, a blank line, then the file list), and the sub-agent reads that file instead of re-deriving it. Until then the sub-agent re-derived the mode keyed on the **commit** SHA, so a rebase that left the tree unchanged was logged as a full review and run as a DELTA, and its file list stopped at GitHub's 30-per-page default. Any uncertain delta — empty, compare failed, or compare at its 300-file cap — falls back to FULL, since a wider review is only ever a comment. Only an unfetchable PR file list SKIPs. A rebase therefore gets a full review, which approves in an `--auto-approve` tick when clean. **One state store** (v0.6.0): `pr_path <kind> <pr>` is the only code that knows a per-PR file name. The kinds are the durable `reviewed` and `carried` (`DURABLE_KINDS`, purged once the PR closes), plus the transients (`TRANSIENT_KINDS`) `pending`, `scope`, `prior` and `findings`. `pr_review_paths`, pre-flight, finish, detection and purge all build paths through it, and so do the tests' seeding helpers; only the tests' literal-path assertions spell names out. `record_write`/`record_read` hold the `reviewed` and `pending` records as `key=value` lines (`commit`, `tree`, `reviewed_at`). They replaced two identical two-line pairs of functions. The reader still accepts the legacy two-line shape, because existing `last-reviewed-*` files persist across the upgrade. `reviewed_at` is GitHub's `submitted_at` from the POST response, so detection compares it with GitHub's `review_requested` time on the same clock. Only a legacy record falls back to the file's mtime, which was the whole mechanism before, and which anything that touched the file could move. The pending record is the **PROCEED token**: `pr_review_finish` without it is a no-op, rather than re-deriving the live head, posting against a commit nobody reviewed, or raising a false "no review body" alert after a SKIP. `pr_clear` removes every transient kind, and purge builds its lists from the same kinds. That also dropped the dead `codeql-wait-*`/`copilot-wait-*` patterns. `test/state.test.sh` covers the store. **Approving is opt-in** (since v0.2.0): the `APPROVE` verdict means only "zero BLOCKERs", and `pr_review_finish` downgrades it to `COMMENT` unless the tick was started as `/review-prs --auto-approve` — `pr_review_init $ARGUMENTS` records that mode in `state/<slug>/auto-approve` (on disk, for the same compaction-immunity reason) and cleanup clears it. Findings post either way; only the review event changes. **Notifications** (v0.3.0) hang off the same point: `pr_review_notify` fires on a posted review (decision + BLOCKER count), a failed POST, and missing or invalid findings — the failure cases being the silent misses, since the bot reviews as *your* GitHub account and GitHub never notifies you of your own actions. Channels are opt-in via `fu-tools` (`review-prs.notify`: `teams`, `bell`; plus `review-prs.teams_webhook`), so no config = silent. The Teams webhook URL is a bearer credential — user config only, and **never logged** (asserted by a test); Power Automate's trigger must be set to *"Anyone"* or an unauthenticated `curl` gets `401 DirectApiAuthorizationRequired`. **Structured findings; bash writes the review** (v0.7.0). The sub-agent's only output is `findings-<pr>.json`: `{"findings":[{severity,text,where?}], "prior":[{status,severity,text,where?}]}`. The findings module in `lib.sh` (`FINDINGS_JQ`, `findings_load`, `findings_blockers`, `findings_body`, `findings_carried`) derives the rest. The blocker count is every `BLOCKER` in `findings`, plus every prior `BLOCKER` that is `STILL OPEN`/`REINTRODUCED`. The verdict is `APPROVE` exactly when that count is zero. The body keeps the pre-v0.7.0 layout. Previously the sub-agent wrote prose, a decision sidecar and a `<!-- DECISION -->` header, and bash regex-parsed the count back out of the prose. That count could contradict the body: on `EntityPlatform` #2172 a RESOLVED prior blocker was notified as `🚧 … 1 blocker(s)` over a body reading "No blockers found". The fix then was a `RESOLVED`-before-the-tag regex plus an "APPROVE forces 0" override. Now the three are views of one list, so the regex, the override, the sidecar and the header are all gone. Validation is **strict**: one bad item rejects the file, which takes the no-findings path (nothing posted, `nobody` notification, reason logged, retry next tick). A review with a finding silently dropped is worse than a retried one. On a successful post, finish writes the durable `carried` kind (`last-findings-<pr>.json`): the current findings plus live priors, with RESOLVED dropped. Pre-flight's `write_prior_findings` copies that into `prior-<pr>.json`. A PR last reviewed before v0.7.0 has no carried findings, so it gets `{"findings":[],"legacy_body":…}` from GitHub, which the brief handles. If the carried write fails, the file is removed rather than left holding an older review's findings. **Review effort is always explicit, never bare** (since v0.3.3): `review-task.md` invokes `/code-review` with a level the sub-agent picks itself — `low` for a small/simple scope, `medium` otherwise — because a bare `/code-review` reuses whatever level was last typed in the invoking context, undefined for a fresh sub-agent. Capped at `medium`; `high`/`xhigh`/`max` are out of scope for an unattended tick. **House rules** (v0.3.4) sit alongside the merit-graded findings in `review-task.md`'s Step 2 — named patterns that are a BLOCKER on their own because the pattern *is* the defect. The first: a method or function the PR **adds or renames** whose name carries the word `Mint`, a stock LLM verb that appears in no codebase here, so its presence says the author never settled what the method does. Matched on **name segments** (camelCase/Pascal/`_`/`-` split, segment == `mint`, case-insensitive) rather than raw substring, or `ConfirmIntent` trips it. House rules deliberately stay out of `pr-review-bot-spec.md`: R31 already admits "documented-rule violation" as a blocker class, and *which* rules a shop documents is not portable. See `plugins/fu-review-prs/docs/orchestrator-subagent-pr-review-bot.md` for the rationale, and `plugins/fu-review-prs/docs/pr-review-bot-spec.md` for the same design as an OS-/language-/forge-agnostic conformance spec (numbered requirements + failure modes, ports, a 34-case test suite, and this bash implementation's known deviations — `flock` holder instead of a TTL lease record, mtime as `reviewed_at` only for pre-v0.6.0 records, non-atomic state writes, `key=value` records rather than JSON).
