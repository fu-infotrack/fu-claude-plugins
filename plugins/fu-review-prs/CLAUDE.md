# fu-review-prs — CLAUDE.md

Read this before changing anything under `plugins/fu-review-prs/`. Repo-wide rules — worktrees,
the install cache, the `fu-tools` config contract, the three registries, and the full
external-dependency list — live in the root `CLAUDE.md`.

## Design

- **PR-review orchestrator** (`fu-review-prs`): all irreversible/external steps (lock, state, GitHub post) are deterministic bash in the orchestrator; the per-PR review runs in a sub-agent whose context never returns. State (`last-reviewed-<pr>`: commit + tree SHA) is namespaced per repo and lives in `~/.claude/pr-review/`, outside the wiped plugin cache. The dedicated review clone is force-reset to a pristine `origin/main` at tick start **and** after each PR via `pr_review_reset_tree` (`fetch` → `checkout -f main` → `reset --hard origin/main` → `clean -fd` → prune all non-`main` local branches). Cross-Bash-call locks use a background `flock` holder process (a normal fd-flock would release when the bash call returns). The pre-flight→post handoff is **disk-based, not context-carried**, so a mid-tick context compaction loses nothing: pre-flight persists `pending-<pr>` (commit+tree) and the sub-agent writes `findings-<pr>.json`; `pr_review_finish <pr>` takes only the PR and recovers commit/tree/findings from disk. **The orchestrator's context sees tokens only** (v0.4.0), because a `/loop` session accumulates every tick's context. `log()` writes to the file and never to stderr, which the Bash tool would capture. Pre-flight prints `PROCEED` followed by the complete Task prompt (`dispatch_prompt`), so the model never assembles it. The sub-agent's whole reply is `DONE`, which the command says to ignore. `test/preflight.test.sh` pins exactly this stdout/stderr shape. `pr_review_finish` prints one status token (v0.8.0): `POSTED APPROVE`/`POSTED COMMENT`, `FAILED`, `NO_FINDINGS` or `NOTHING_PENDING`. Before that it printed nothing, so a silent finish looked the same whether the review posted or failed, and the orchestrator could only report "can't confirm". The reason for a non-posted outcome stays in the log. **Pre-flight owns the review scope** (v0.5.0). `write_review_scope` picks the mode from the **tree** SHA, the same key the state uses: no state or an unchanged tree (a re-request) → FULL; a changed tree → DELTA over the PR's files (every page of `pulls/files`) ∩ the files in `compare/<last>...<head>`. It writes `scope-<pr>.txt` (a `REPO`/`HEAD`/`MODE`/`DELTA_BASE` header, a blank line, then the file list), and the sub-agent reads that file instead of re-deriving it. Until then the sub-agent re-derived the mode keyed on the **commit** SHA, so a rebase that left the tree unchanged was logged as a full review and run as a DELTA, and its file list stopped at GitHub's 30-per-page default. Any uncertain delta — empty, compare failed, or compare at its 300-file cap — falls back to FULL, since a wider review is only ever a comment. Only an unfetchable PR file list SKIPs. A file list that fetches **empty** (an empty-commit PR) is not a failure (v0.9.2): pre-flight writes the durable `empty` record (commit + tree) and SKIPs, and detection skips any PR whose `empty` record matches its live head tree — re-request or not — until a push moves the tree. Before that it was treated as a fetch failure, so nothing was recorded and `EntityPlatform` #2863 was re-selected and re-SKIPped every tick. A rebase therefore gets a full review, which approves in an `--auto-approve` tick when clean. **One state store** (v0.6.0): `pr_path <kind> <pr>` is the only code that knows a per-PR file name. The kinds are the durable `reviewed`, `carried` and `empty` (`DURABLE_KINDS`, purged once the PR closes), plus the transients (`TRANSIENT_KINDS`) `pending`, `scope`, `prior` and `findings`. `pr_review_paths`, pre-flight, finish, detection and purge all build paths through it, and so do the tests' seeding helpers; only the tests' literal-path assertions spell names out. `record_write`/`record_read` hold the `reviewed`, `pending` and `empty` records as `key=value` lines (`commit`, `tree`, `reviewed_at`). They replaced two identical two-line pairs of functions. The reader still accepts the legacy two-line shape, because existing `last-reviewed-*` files persist across the upgrade. `reviewed_at` is GitHub's `submitted_at` from the POST response, so detection compares it with GitHub's `review_requested` time on the same clock. Only a legacy record falls back to the file's mtime, which was the whole mechanism before, and which anything that touched the file could move. The pending record is the **PROCEED token**: `pr_review_finish` without it is a no-op, rather than re-deriving the live head, posting against a commit nobody reviewed, or raising a false "no review body" alert after a SKIP. `pr_clear` removes every transient kind, and purge builds its lists from the same kinds. That also dropped the dead `codeql-wait-*`/`copilot-wait-*` patterns. `test/state.test.sh` covers the store. **Approving is opt-in** (since v0.2.0): the `APPROVE` verdict means only "zero BLOCKERs", and `pr_review_finish` downgrades it to `COMMENT` unless the tick was started as `/review-prs --auto-approve` — `pr_review_init $ARGUMENTS` records that mode in `state/<slug>/auto-approve` (on disk, for the same compaction-immunity reason) and cleanup clears it. Findings post either way; only the review event changes. **Approval is also file-gated** (v0.10.0): an `APPROVE` survives the opt-in only when every PR file — all of `pulls/files`, never the DELTA scope, plus each rename's `previous_filename` — matches `LOW_RISK_PATHS_DEFAULT` (docs, tests, UI) or the fu-tools array `review-prs.low_risk_paths`, which replaces it. Pre-flight's `classify_pr_files` writes the transient `gate` kind (`gate-<pr>.txt`: `low-risk` or the first offending path); finish downgrades to `COMMENT` on anything else, including a missing record. **Notifications** (v0.3.0) hang off the same point: `pr_review_notify` fires on a posted review (decision + BLOCKER count), a failed POST, and missing or invalid findings — the failure cases being the silent misses, since the bot reviews as *your* GitHub account and GitHub never notifies you of your own actions. Channels are opt-in via `fu-tools` (`review-prs.notify`: `teams`, `bell`; plus `review-prs.teams_webhook`), so no config = silent. The Teams webhook URL is a bearer credential — user config only, and **never logged** (asserted by a test); Power Automate's trigger must be set to *"Anyone"* or an unauthenticated `curl` gets `401 DirectApiAuthorizationRequired`. **Heartbeat** (v0.9.0): `pr_review_heartbeat` pings a Cloudflare Worker (`worker/`) right after `pr_review_init` takes the lock — so `NO_WORK` ticks ping and `LOCKED` ticks don't, and a wedged lock goes red rather than staying green. On when `review-prs.heartbeat_url` + `heartbeat_token` are both set (user config; the token goes to curl on **stdin**, never argv or the log); `heartbeat_footer: true` adds the repo's badge to the review footer. The Worker keeps one D1 row per repo, `last_ping` on the **Worker's** clock (the ping has no body), and draws the badges itself: live = last ping ≤ **15 min**, a fixed value chosen by the user (loops tick about every 10 min; a learned interval was rejected). `/badge.svg` lists live bots only — one row per repo with its last ping time, stacked vertically (v0.9.1) — so a dead or retired bot drops off with no pruning. The dot is an SVG `<circle>`, not an emoji, so the colour never depends on the viewer's font; month names are a fixed table, since ICU's short months vary ("Sep" vs "Sept"). **Nothing account-specific is committed**: `wrangler.jsonc` has no `account_id` or `database_id`. wrangler ≥ 4.45 auto-provisions D1 and re-finds it by binding name, and `CI=true` on deploy stops it writing the id back. The Worker runs `CREATE TABLE IF NOT EXISTS` itself (once per isolate), because `d1 execute --remote` without a `database_id` needs a very recent wrangler. `badge-lib.mjs` is pure and `node --test`-covered; the D1 handler is not tested (no `package.json`/Miniflare here). **Structured findings; bash writes the review** (v0.7.0). The sub-agent's only output is `findings-<pr>.json`: `{"findings":[{severity,text,where?}], "prior":[{status,severity,text,where?}]}`. The findings module in `lib.sh` (`FINDINGS_JQ`, `findings_load`, `findings_blockers`, `findings_body`, `findings_carried`) derives the rest. The blocker count is every `BLOCKER` in `findings`, plus every prior `BLOCKER` that is `STILL OPEN`/`REINTRODUCED`. The verdict is `APPROVE` exactly when that count is zero. The body keeps the pre-v0.7.0 layout. Previously the sub-agent wrote prose, a decision sidecar and a `<!-- DECISION -->` header, and bash regex-parsed the count back out of the prose. That count could contradict the body: on `EntityPlatform` #2172 a RESOLVED prior blocker was notified as `🚧 … 1 blocker(s)` over a body reading "No blockers found". The fix then was a `RESOLVED`-before-the-tag regex plus an "APPROVE forces 0" override. Now the three are views of one list, so the regex, the override, the sidecar and the header are all gone. Validation is **strict**: one bad item rejects the file, which takes the no-findings path (nothing posted, `nobody` notification, reason logged, retry next tick). A review with a finding silently dropped is worse than a retried one. On a successful post, finish writes the durable `carried` kind (`last-findings-<pr>.json`): the current findings plus live priors, with RESOLVED dropped. Pre-flight's `write_prior_findings` copies that into `prior-<pr>.json`. A PR last reviewed before v0.7.0 has no carried findings, so it gets `{"findings":[],"legacy_body":…}` from GitHub, which the brief handles. If the carried write fails, the file is removed rather than left holding an older review's findings. **Review effort is always explicit, never bare** (since v0.3.3): `review-task.md` invokes `/code-review` with a level the sub-agent picks itself — `low` for a small/simple scope, `medium` otherwise — because a bare `/code-review` reuses whatever level was last typed in the invoking context, undefined for a fresh sub-agent. Capped at `medium`; `high`/`xhigh`/`max` are out of scope for an unattended tick. **House rules** (v0.3.4) sit alongside the merit-graded findings in `review-task.md`'s Step 2 — named patterns that are a BLOCKER on their own because the pattern *is* the defect. The first: a method or function the PR **adds or renames** whose name carries the word `Mint`, a stock LLM verb that appears in no codebase here, so its presence says the author never settled what the method does. Matched on **name segments** (camelCase/Pascal/`_`/`-` split, segment == `mint`, case-insensitive) rather than raw substring, or `ConfirmIntent` trips it. House rules deliberately stay out of `pr-review-bot-spec.md`: R31 already admits "documented-rule violation" as a blocker class, and *which* rules a shop documents is not portable. See `plugins/fu-review-prs/docs/orchestrator-subagent-pr-review-bot.md` for the rationale, and `plugins/fu-review-prs/docs/pr-review-bot-spec.md` for the same design as an OS-/language-/forge-agnostic conformance spec (numbered requirements + failure modes, ports, a 34-case test suite, and this bash implementation's known deviations — `flock` holder instead of a TTL lease record, mtime as `reviewed_at` only for pre-v0.6.0 records, non-atomic state writes, `key=value` records rather than JSON).
- **REST only, and a review worktree** (v0.12.0), so it runs in Claude Code cloud sessions. Cloud sessions answer every GitHub GraphQL request with HTTP 403, and `gh repo view`, `gh pr list`, `gh pr view`, `gh issue view` and `gh pr checkout` are all GraphQL underneath. Until v0.12.0 `REPO` came from `gh repo view`, so in a cloud session it was empty and every tick returned `NO_WORK` without ever looking at a PR. Every GitHub call in `lib.sh` and in `review-task.md` is now REST: `repos/<repo>/pulls?state=open` with `requested_reviewers` for detection (which also lifts `gh pr list`'s 30-PR default limit), `pulls/<n>` for head, author, state and title, `issues/<n>` and `issues/<n>/comments` for intent, and `gh pr diff`, which is REST. `REPO` comes from `remote.origin.url` as configured, before any `insteadOf` rewrite, and `PR_REVIEW_REPO` overrides it. `test/cloud-session.test.sh` fails on any GraphQL-backed `gh` command in `lib.sh`, and the other suites' `gh` stubs reject them. One thing has no REST equivalent: `closingIssuesReferences`. The brief finds closing keywords in the PR body instead, so an issue linked only through the PR's Development sidebar is missed. The REST timeline's `connected` event does not name the issue, and none of `EntityPlatform`'s last 40 closed PRs had one. **The checkout is never touched**: in a cloud session the cwd checkout is the session's own, holding the user's branch, and the old `pr_review_reset_tree` (`checkout -f main`, `reset --hard`, `clean -fd`, delete every non-`main` branch) would have destroyed it. Reviews now run in a detached worktree of it at `~/.claude/pr-review/worktrees/<slug>` (`REVIEW_DIR`), created on first use and recreated if it disappears. Pre-flight fetches `refs/pull/<n>/head` and checks out the PR's head commit there, so the sub-agent reads, greps and blames the reviewed code. `REVIEW_DIR` rides in the dispatch prompt, because every Bash call starts in the cwd checkout. `pr_review_reset_tree` returns the worktree to a clean `origin/main` at tick start and after each PR. It fetches main with an explicit `+refs/heads/main:refs/remotes/origin/main` refspec, since a session clone's fetch refspec may be narrower, and it never deletes a branch: a detached worktree creates none. **A failed open-PR listing no longer purges**: purge read an empty listing as "no PR is open" and deleted every durable record. It now keeps them for that tick and logs a warning.
- **No `gh api --paginate`; explicit pages** (v0.12.1). `--paginate` follows GitHub's `Link: rel="next"`, which names the repo by numeric ID (`repositories/<id>/...`). A cloud session's GitHub proxy answers that form with HTTP 403 ("Numeric-ID repository paths … are not supported through this proxy"), so page 1 landed, page 2 failed, and the whole call failed. The live case was `write_review_scope`: `pulls/<n>/files` defaults to 30 per page, so every PR with more than 30 files SKIPped ("could not fetch the PR's file list"), detection re-queued it, and it was skipped every tick. `EntityPlatform` #3333 (252 files) was the repro. Every list in `lib.sh` (files, open PRs for detection and purge, 👀 reactions) now goes through `gh_api_pages <path> <jq>`. It asks for `per_page=100&page=N` on the `repos/<owner>/<name>` path, counts items on the raw page (one item can print 0 or many jq lines), stops on a short page, and returns 1 if any page fails. So scope still SKIPs and purge still keeps records on a failed listing, while detection queues what the pages before the failure named. It stops at 30 pages, GitHub's own 3000-file cap on `pulls/<n>/files`. `review-task.md` tells the sub-agent to page issue comments the same way. `test/cloud-session.test.sh` fails on any `gh api … --paginate` in `lib.sh` or `review-task.md`. The `gh` stubs serve GitHub-shaped pages and reject `--paginate` past page 1, as the proxy does.
- **`/review-pr`: one PR per run, state on GitHub** (v0.13.0). For a cloud scheduled task on a GitHub `pull_request.review_requested` trigger: a fresh session per event, so `pr_review_one` skips the lock, detection, purge and heartbeat and runs the loop's own pre-flight → Task sub-agent → `pr_review_finish`. The sub-agent hop stays (the user asked about inlining) because it keeps the context that reads untrusted PR content away from the post step: inline, an injected instruction could make the model `gh api … event=APPROVE` itself. **The PR**: an argument (`N`, `#N`, or a URL whose repo re-sources `lib.sh` under `PR_REVIEW_REPO`), else the single open PR whose head is `HEAD` (`commits/<sha>/pulls`) — a PR-triggered session's first repo is cloned at the PR head. **The guard is the only reviewer filter**: GitHub triggers have none, and team auto-adds fire `review_requested` too, so it reviews only when the user is in `requested_reviewers` **by login**. **The mode is per PR**, the transient `mode` kind (`single`, plus `auto-approve`): `auto_approve_enabled <pr>` prefers it over the tick-wide `AUTO_APPROVE_FILE`, so a local `/review-pr` never reads or flips a running loop's flag; `single_run` also drops the heartbeat badge from the footer (no loop keeps it live). A pre-flight SKIP clears it. **State on GitHub** (both commands): finish appends `<!-- fu-review-state:<base64 {v,commit,tree,carried}> -->` as the body's last line, and `pr_review_preflight` calls `hydrate_from_github` when there is no local `reviewed` record — the only way a fresh cloud session gets DELTA scope and structured priors. It reads **only the user's own** marked reviews (anyone can post the marker) and **only the latest** (an older review's state is stale, so a latest one without state restores nothing). `carried` is dropped from the comment when the body would pass GitHub's 65,536-character limit. `fetch_prior_findings` strips the comment from a legacy body. **Duplicates**: the `pending` record now stamps the dispatch time (its `reviewed_at` field), and finish prints `DUPLICATE` without posting when one of the user's marked reviews landed on the same `commit_id` at or after it. Fails open. `test/review-pr.test.sh` covers all of it. Cloud facts this rests on (code.claude.com/docs/en/routines, cloud-environments, 2026-10): no `review_requested`-by-user filter, no documented PR-number injection, every event its own session with no dedupe, and repo/user `enabledPlugins` are not installed in cloud sessions — the user's environment installs the plugin itself, auto-updating.
- **The review routine: `/review-pr` without the plugin** (v0.14.0). A cloud routine installs no plugin, so `/code-review` and the `Task`-from-a-command flow are unavailable to it. `routines/review-pr.md` holds the setup table and the prompt the user pastes into the routine. The routine attaches `InfoTrackGlobal/EntityPlatform` **first**, because only the first repo is cloned at the PR head, and this repo second, on `main`. The prompt locates both clones by origin URL, writes `~/.claude/pr-review/routine.env`, and runs `pr_review_one --routine`, the same guard, pre-flight, state and finish as `/review-pr`. The orchestrator is **Haiku** (the routine's model, UI-only) and does mechanical work only: it copies the printed blocks into Agent calls with `model: opus` and `effort: medium`. **The size split is bash's**: `routine_scope_size` counts the scope's files and changed lines (`additions+deletions` from `pulls/files`, whole-PR per file, so a DELTA over-counts toward FANOUT, and a failed count also means FANOUT). At ≤ 5 files and ≤ 200 lines `routine_prompts` prints `SINGLE` and one `--- reviewer all ---` block, which writes `findings-<pr>.json` and re-checks priors itself. Above that it prints `FANOUT` with three reviewer blocks (`correctness`, `security`, `intent`, which also covers scope, repo rules, the `Mint` house rule and doc/comment consistency) writing the transient `part_<dim>` kinds (`findings-<pr>.<dim>.json`). A `--- merger ---` block follows, which dedupes, verifies BLOCKERs, re-checks priors and writes the findings file. The mode file records `routine` (footer) and `fanout`, and **finish refuses an incomplete FANOUT**: any missing or invalid part means `NO_FINDINGS`, nothing posted, because a review missing a dimension reads clean where nobody looked. The briefs (`routine-reviewer.md`, `routine-merger.md`) carry their own review method and read the target repo's `CLAUDE.md` files for its rules. They deliberately do not reuse EntityPlatform's `.claude/agents` reviewers, which point at `.claude/rules/` and `.claude/skills/review-checks/` (absent on its `main`), and whose `security-analyser` pauses for the user when a plugin is missing. Posting is always COMMENT, drafts included. `test/review-pr.test.sh` pins the routine's output, the threshold, DELTA counting and the incomplete-FANOUT refusal.
- **`/review-prs` is model-invocable** (v0.11.0). v0.3.6–v0.10.2 set `disable-model-invocation: true` (#55) so it would only run when typed, but that also blocks the Skill tool — an agent driving a self-paced `/loop` or a sub-agent could not start a tick. The flag is gone; the cost is the command's description in every session's context. Don't re-add it.
